# Maintenance workflow

Follow [AGENTS.md](../../AGENTS.md). Use `gh` for GitHub and `lark-cli` for the bound group; verify commands and identities with their current help/schema. Run the separately installed external controller from the product control checkout: `cz-maintenance COMMAND`, or use `cz-maintenance --repo /absolute/control/checkout COMMAND`. This repository contains no maintenance implementation or wrapper; only docs, AGENTS.md and Action AI review remain here.

<a id="本机记录"></a>

## Runtime and versions

- Both roles share `cz-maintenance/` under `git rev-parse --git-common-dir`; `config.json`, `native-handoff.md`, `claims/`, `tasks/` and `control/` live there. Run `init` to index legacy tasks and `status` to inspect tasks, permissions and receipts. Preserve legacy state, configuration, cursors and worktrees; new progress/source mappings use `native-state.json`. Legacy executor/interval fields do not schedule native jobs.
- Read `config.json.permissions` each round. Existing authorization covers task-branch pushes, PRs, original-thread GitHub/Bot replies, guarded merges and nightly releases. Keep `release: false`, `releaseNightly: true`, `releaseStable: false`; Bot replies stay in the bound original group/thread. Check each external action's authorization.
- The control checkout (`native.maintenanceRoot`) is a clean clone on `main`. Each role round starts with `sync ROLE`, which fast-forwards it to `origin/main`, refuses local edits or another branch, and lists in `changedRules` the rule and note files that changed since that role last confirmed a read; reread those, then confirm with `rules-read ROLE SHA`. Start loops/subagents and invoke maintenance tools there; edit/test source in the task worktree. Keep source and release SHAs distinct.
- Develop repository docs/AGENTS/Action review changes in an exclusive worktree from updated `origin/main`. Finish the scoped implementation and local package-scoped checks before pushing the task branch and opening or updating its PR, then run independent exact-head review (`cz-maintenance review TASK PR`) on the open PR before merging; consolidate fixes for the same task on that branch. The next `sync` makes merged rules available, and the role must reread them. Controller implementation and tests belong to the external `cz-cli-maintainer` project; review, test and deploy its commit separately. Product sync never upgrades controller code. Keep maintenance changes out of product-fix diffs.
- On takeover, read all of `native-handoff.md`, not its tail: pending actions sit in the middle, the closing summary may not repeat them. Then reconcile actual tasks, delegates and receipts with `status`. Reuse IDs, worktrees and source mappings. Historical summaries cannot override current authorization, completion receipts or satisfied release conditions.
- Each task records sources, acceptance criteria, owner, worktree, `baseSha`, `headSha`, `reviewedSha`, validation, review outcome, external actions, blockers and next steps. Link cross-channel reports of the same problem to it. Use `task github:<owner>/<repo>:<number>` or `task lark:<chat_id>:<message_id>`; `register ITEM.json` deduplicates sources, `task-patch TASK --json JSON [--increment-attempts]` updates mutable fields atomically under the state lock (enforcing `maxTaskAttempts` circuit-breaking), and `save TASK.json` saves full task payloads. Keep task bodies and temporary JSON private.

<a id="自主推进与决策"></a>

## Decisions

Own the problem as a maintainer with repository access and take responsibility for resolving it. Use the information already available and your tools to investigate and advance the work. When user input is needed, explain what their information or decision will help resolve and ask someone able to provide it. Keep progressing on work that does not depend on the missing information.

Proceed on clear requirements and routine implementation choices. Existing behavior and tests establish compatibility, not product authorization.

Before replying to a bug report or broad feature request, inspect current `origin/main`, git history, related tasks, and published releases first, and lead with concrete codebase facts (naming existing commands/flags that already address part of the request and pinpointing which surface still lacks support):
- **Already fixed in the latest Stable release**: recommend updating first (`cz-cli update` or the official installer) and state what diagnostic evidence to share only if the issue still reproduces after upgrading — do not block progress or send a round-trip question just to ask `cz-cli --version`.
- **Fixed only in a Nightly (`dev-v...`) pre-release**: explain that the fix is currently available on the opt-in Nightly channel (with the explicit versioned installer command) and is not yet in a Stable release; do not promise when Stable will ship or imply default `cz-cli update` installs Nightly builds.
- **Merged on `origin/main` pending Nightly publication**: advance or wait for the verified Nightly artifact before advising the user to upgrade.
- **Still reproduces on `origin/main`, needs scope disambiguation, or depends on private deployment state**: summarize what current `origin/main` already supports versus where support is missing, ask only for the specific target surface, decision, or private environment detail needed, and never ask for `cz-cli --version` unless a verified behavioral difference across versions changes the diagnosis or next action.

If a product decision still affects contracts, data visibility or authorization, pause only dependent work. Record verified facts, the missing decision, one concrete question, a recommendation and its impact. Continue other work; avoid repeated investigation or reminders without new evidence. Resume when the stated condition is met: “pause until fixed and reviewed” does not require another approval. Failed CI or unmet acceptance criteria still block delivery.

## Wakeups and monitoring

The [Codex service](codex.md) owns scheduling and intake. It scans GitHub and Feishu every minute, persists wakeups and timers, pre-compiles a redacted `WakeBriefing` snapshot for each round, and coordinates both foreground role rounds and bounded asynchronous background delegates (`cz-maintenance delegate`). A busy, paused or failed model does not stop source scans. Do not create native Cron/Monitor jobs, persistent model-owned listeners, competing coordinators or duplicate scans from a service-owned round. Read `service status` for source health, active delegates and pending work; failed reads never count as coverage.

The Worker reconciliation timer runs every five minutes and the Curator timer every day. Worker ticks are discarded when no input, active background delegate, or active unsubscribed task needs work (unless `config.idleBacklog` explicitly opts into bounded daily backlog draining when all queues are idle). The Supervisor probes PR check readiness (`awaiting-merge`), level-triggered open repository PR states (`reconcileOpenPulls`, catching orphaned green, failed, conflicting, or `CHANGES_REQUIRED` PRs that lack an active wait), `main` CI readiness (coalescing multiple `awaiting-nightly` tasks into a single Nightly cut), active Nightly workflows/COS artifacts, and task subscriptions (`cz-maintenance wait TASK ...` / `unwait TASK`) without invoking a model round until an actionable transition occurs. The outer self-maintenance loop (`cz-self-maintenance`) also delivers a daily Chinese summary of Worker progress and evidence-backed improvement suggestions (`cz-maintenance ops digest`) on the first eligible self-maintenance tick at or after `19:30` Asia/Singapore (idempotent once per local day). Save future checks as subscriptions, background delegates, or durable one-shot followups before ending a round. Synchronous subagents must finish within the round; asynchronous work across rounds must be dispatched exclusively through `cz-maintenance delegate dispatch`. Scheduling can lag during outages or long rounds; intervals are not response guarantees.

The service uses Feishu history polling and does not claim a live long connection. Legacy Claude deployments used native Monitor and `watch github`; those jobs and consumers must be stopped before service takeover. Do not send Feishu test or diagnostic messages. See [Feishu prerequisites](INDEX.md#feishu-prerequisites) when restoring a live event listener in a future design.

A terminal provider failure, timeout or interrupted execution pauses that role. Codex's own recoverable stream notices stay within the current execution; only its confirmed completion can establish recovery. Intake continues. Before `service resume`, reconcile task worktrees, delegates, PRs, releases, outgoing replies and ambiguous receipts, then record what was checked. Restarting the daemon does not clear a role pause or replay a provider turn.

## Task lifecycle

1. Read current configuration, `WakeBriefing`, handoff, existing tasks, and the original discussion to verify the latest source context and human/maintainer decisions. Resolve stable source IDs before claiming/registering; append updates to existing tasks.
2. Claim the task atomically via `cz-maintenance claim TASK --owner OWNER [--note TEXT]` (which records PID + process-start identity and automatically recovers dead-PID stale claims while rejecting live conflicts; inspect with `cz-maintenance claims` and release with `cz-maintenance release-claim TASK`). Modify only your own tasks/control records; reconcile ownership first.
3. For a new fix, prepare an exclusive worktree from updated `origin/main` via `cz-maintenance worktree TASK [--branch SHORT-HYPHEN-NAME]` (which records `baseSha` and `worktree` and symlinks baseline `node_modules` when `bun.lock` matches). When a root-cause hypothesis is uncertain, run `cz-maintenance challenge TASK HYPOTHESIS_FILE` (or dispatch `--kind challenge`) before coding to test the diagnosis against counterevidence in the codebase. When host-private E2E test profiles (`CLICKZETTA_TEST_HOME`, `CZ_E2E_PROFILES`, `CZ_E2E_CURL`) are injected on the maintenance server for trusted tasks (never for external fork PRs and never in GitHub Actions), reproduce and verify real Studio/Lakehouse API contracts via `(cd packages/cz-cli && bun ./src/main.ts --profile uat <command>)` or `"$CZ_E2E_CURL" uat GET /path` — prefix temporary Studio tasks/tables with `cz_e2e_`, delete them immediately after verification, and never commit or echo credentials or tokens. Run scoped implementation either within the current round using the [implementer brief](prompts/delegate-implement.md) or asynchronously via `cz-maintenance delegate dispatch TASK --kind implement --worktree WORKTREE --prompt-file BRIEF_FILE` (strictly one active background delegate per task; the service wakes the Worker with `delegate-done:<taskId>:<delegateId>` when finished). PR reviews retain the PR head and actual merge-base; save a handoff and reconcile unexpected history before transplanting changes.
4. Once implementation and local package-scoped checks succeed, push the task branch and open or update the pull request within configured permissions, recording `headSha` and `pullRequestNumber` via `cz-maintenance task-patch TASK --json ...`.
5. From the control session (or via `delegate dispatch TASK --kind review --pr PR`), run `cz-maintenance review TASK PR` (optionally paired with heterogeneous `native.reviewModel` and `native.review.consensus` dual-model verification): it fetches and checks out a clean detached worktree at the exact remote PR head, runs an isolated read-only review against the original request/decisions and diff without inheriting implementation chat, atomically writes an exact-head JSON receipt in `outbox/reviews/`, and records `reviewedSha`, `phase: review` and `status: completed` on `APPROVE` with zero blocking findings. Each review receipt records `coreAcceptanceMet` plus an orthogonal finding `category` (`unmet_core_request`, `regression_vs_main`, `security_leak`, `guard_or_test_bypass`, `adjacent_or_preexisting`, or `hypothetical_edge_case`): findings in `adjacent_or_preexisting` or `hypothetical_edge_case` are mechanically capped at non-blocking severity so grade inflation cannot stall a verified core fix. Once `task.attempts >= 2` and `coreAcceptanceMet === true`, converge rather than expanding the diff (revert opportunistic edits to adjacent files if needed and split a follow-up issue); if a task ever reaches `maxTaskAttempts` without converging, the Supervisor sends a one-time Chinese escalation to the operator group rather than parking silently behind a self-authored PR wait. Read the full independent review report before merging: keep the current PR focused on its reported scope rather than expanding into unrelated refactors, and when `APPROVE` notes worthwhile out-of-scope `medium`/`low` defects (or implementation uncovers adjacent bugs), search open/closed issues to avoid duplicates and open a focused follow-up GitHub issue (`curator: ...` / `follow-up: ...`, citing the PR and exact `file:line`) when `permissions.postGithub` allows so intake / `idleBacklog` handles it as an independent task. Any source change requires a new review; retain failures when returning for fixes. Preview with `merge TASK PR`, then execute with `merge TASK PR --merge`. Require an exact-head `APPROVE` receipt in `outbox/reviews/` before merging; the merge guard verifies remote SHA, the recorded review, the `outbox/reviews/` receipt on the exact final head, and CI, then records the merge commit. Only administrators bypass the PR-approval rule; other contributors need one approval. Keep main deletion/force-push protections.
6. For merged product fixes, follow [release rules](../engineering/releases.md): run local pre-release E2E smoke verification on the maintenance host (`cz-maintenance e2e-smoke MERGED_SHA`, enforced automatically before tagging when `config.e2e.requiredBeforeNightly` is enabled — never in GitHub Actions), publish nightly only (`cz-maintenance nightly --auto MERGED_SHA --publish`, which queries the live Nightly channel for monotonic semver/timestamp progression), and verify artifacts (manifest, versioned installer, archive SHA-256, and isolated `bwrap` `--version` smoke check on Linux hosts where `/usr/bin/bwrap` is present and PID 1 is `systemd`) before reporting success. Docs/tests/maintenance-only changes need no release. Different tasks may run concurrently with separate claims, delegates and worktrees; never duplicate implementation of one task. Keep review, fixes and delivery on that task. Release your claim only after all its writers stop.
7. Clean up what the task created, on the wake after it reaches a final state and its writers have stopped. For a task with a pull request, final means the pull request is merged or closed; for a task without one, it means status `completed` or `ignored`. A task approved in review but not yet merged keeps its worktree. Ownership follows the task record, not the session: a worktree named in a task's `worktree` field belongs to that task, whichever session created it, and the Worker cleans it. A reviewer removes its own worktree when it reports. Before removing a task worktree, confirm that `git -C WORKTREE status --porcelain` is empty and that its `HEAD` is safe: `git -C WORKTREE branch -r --contains HEAD` lists a branch, `HEAD` equals the pull request's recorded head SHA, or `HEAD` is the task's `baseSha` with nothing committed on top. Only then run `git worktree remove WORKTREE` without `--force`, delete the local branch (a squash merge needs `git branch -D`, which is why the check comes first), and run `git worktree prune`. If a check fails, save a handoff and leave the worktree. Worktrees that no task record names need item-specific approval.

`cz-test/test` must pass; other failed/pending checks block by default. Only an explicit `mergePolicy.informationalWorkflows` entry may treat the known failing `Claude Code Review` workflow as informational. It never replaces independent review or exempts product tests. Removing it restores full CI blocking.

## Intake and delivery

Run `intake github` and `intake feishu` and process their durable `pending` queues. GitHub coverage includes issues, PRs, regular comments, reviews and inline comments; Feishu includes new roots and known old-thread replies with an overlap window. The first Feishu scan registers all accessible threads; record any configured lookback limit and actual `coverage`. Do not claim coverage outside that range. Unchanged PR heads, empty roots or old cursors do not prove full coverage. Pagination/context failures must not advance the successful cursor.

Read full source/context from each summary's `file` or `intake show SOURCE EVENT_KEY`. Resolve its task, save the association and reply receipt or explicit disposition, then acknowledge:

```sh
cz-maintenance intake ack feishu EVENT_KEY --task TASK_ID --note 'Linked to the existing task; reply receipt saved'
cz-maintenance intake ack github EVENT_KEY --note 'Duplicate; original discussion and reason recorded'
```

`--task` must exist; supply at least `--task` or `--note`. Fetching only queues input; it does not finish processing. Keep unread/unhandled items pending across rounds and never report “no new feedback” while they remain. Blocked implementation must not stop other intake/replies.

Each source has one scan owner. Network pagination holds a separate scan lock so Workers can acknowledge existing input during a slow scan. Publication briefly locks and rereads the current ledger, preserving acknowledgements before adding new input and advancing the fetched cursor. A failed fetch never publishes partial input or rolls back an acknowledgement. Stop previous scanner processes before upgrading the intake implementation.

Read Feishu as the authorized user; reply as the Bot already in the group. Route all Bot replies through maintenance's `lark-cli im +messages-reply --reply-in-thread --idempotency-key` wrapper and outbox. Phase values are protocol literals: `接单`, `阻碍`, `审查完成`, `发布完成`.

```sh
cz-maintenance reply TASK 阻碍 --event STABLE_EVENT --text-file draft.txt
cz-maintenance reply TASK 阻碍 --event STABLE_EVENT --text-file draft.txt --send
```

The first command previews. Use one stable event ID per real state change, such as `blocker-missing-scope` or `review-<SHA>`. Retries keep its ID and text. Under an atomic lock, the tool allocates `<task>-<phase>-<sequence>` only for new events and reuses existing keys. It saves target, text, key and `sending` before dispatch, then `sent` and `message_id` on success. Inspect receipts with `status`.

Timeout/ambiguous outcomes stay `unknown` and block later sends to that target. Reconcile the original thread's time, Bot identity and text before manually recording the receipt. There is no server lookup by key; deduplication lasts one hour. Never bypass unknown outcomes with a new key/sequence or a later retry window.

<a id="对外回复"></a>

## Replies and documentation

Lead with the answer to the recipient's question or the action they can take. Include investigation details only when they help the recipient understand or act on that answer. Write Feishu group Bot replies in Simplified Chinese, and write GitHub issue/PR comments, commit messages, and PR text in English; preserve literal CLI flags, commands, identifiers, and error strings. Report meaningful progress without repetition, distinguish fixes, validation, merges and verified releases, and link evidence when useful.

Follow [verification rules](../engineering/verification.md), update affected domain contracts with behavior changes, and keep task logs private.

<a id="两个角色与反思记录"></a>

## Roles and memory

The [Worker](prompts/worker.md) coordinates both channels; source identities, destinations and authorization remain separate. Record each delegate/worktree and check liveness before recovery. If a delegate is gone, reconcile its worktree/task before resuming or replacing it. Subagents add no permanent roles.

The [Curator](prompts/curator.md) reads what actually happened once a day: session transcripts, issues, pull requests, comments, reviews, Feishu threads, runtime records and commits. It decides what is worth keeping and how to organise it; today's topics are [misunderstandings](understanding.md), [human decisions](decisions.md) and [recurring failures](recurring-failures.md), and it may reshape them. It reports leftover worktrees and finished delegates to the Worker and removes only the editor worktrees it recorded under the [memory protocol](memory-workflow.md). Preserve coverage cursors; no findings means no edits. Route code faults to Worker tasks instead of running a second implementation queue; review each task independently.

Read relevant originals through the [memory index](memory/INDEX.md), and follow the [memory workflow](memory-workflow.md) for new lessons, counterevidence and useful usage feedback. Fresh editors verify evidence, expiry conditions and index consistency; offline cases check subsequent decisions. Publish only confirmed, public long-term knowledge. Keep pending decisions/private evidence in runtime `control/daily-decisions.md`; consult original replies, close answered blockers and update tasks instead of asking again. Unresolved suggestions are not policy.
